# 闹钟实验计划

本计划用于区分 OriginOS 的启动限制、Android 15 的音频焦点限制和应用自身问题。关联任务：[OriginOS 闹钟可靠性](2026-11-17-OriginOS闹钟可靠性.md)。

更新日期：2026-11-17。已完成 E0、E1/E4 部分对照和 [E3 主动移除卡片实验](E3-2026-11-17/前台等待服务.md)。16:11 的 SDK 34 样本在无卡片、锁屏状态播放，用户确认听到，60 秒自动停止；系统上划清理仍会停用应用。[正式播放器接入](2026-11-17-正式播放器后台运行接入.md)已完成，targetSdk 37 包已覆盖安装并有一次无卡片锁屏听感确认；重复与长期验证仍待执行。以下待办不代表已验证。

## 下一步执行顺序

当前范围限定为单个 App、普通权限；不采用独立守护 App、Shizuku、root 或依赖 ADB 常驻的产品方案。ADB 只作为开发验证工具。

1. **恢复正式播放器并接入主动退出卡片。** 用户已明确选择恢复仓库已有播放器。复用现有任务、播放和数据保存逻辑；在有待执行闹钟时，由可见页面启动符合用途的前台等待服务，确认成功后再移除自己的任务。服务未准备好、权限拒绝或没有可用任务时明确反馈。播放、等待、取消各自有清理路径。当前正式模块 targetSdk 37，不能把 SDK 34 的单次样本直接当作正式包已通过。
2. **验证任务栈与退出。** 普通打开、重复点击图标、通知返回、设置页返回后退出均应无残留卡片；避免依赖测试时的 CLEAR_TASK。区别 App 自己退出与用户手动上划，保留手动上划失败的说明。
3. **同包双进程互保对照。** 仅在实验包实现最小 player/guard 双进程。先验证单进程被终止后的恢复，再比较手动上划与锁屏；记录两端 PID、包 stopped、预约、恢复延迟。共享任务状态通过明确的单一数据拥有者/IPC 管理，不能直接把单进程 SharedPreferences 当成跨进程可靠同步。主动取消必须终止双方恢复逻辑，限制重试，避免互相拉起死循环。
4. **SDK 37 与重复验证。** 在同一源码上比较 34/37，并回切复测；补足至少三次有效样本。实际听感必须单独确认，未留意不能计成功。
5. **普通权限兜底。** 继续排查 vivo 自启动条目为何未显示，单独测试自启动、关联启动与后台耗电策略；卡片锁定只作为兜底，分别验证手动上划和一键清理。
6. **长期验收。** 未充电长锁屏、隔夜、重启后重建计划、耳机路由与音量、多个任务及取消/修改、文件失效。短时通过后才决定正式承诺。

实验 App 按用户要求改为 20 秒等待、60 秒播放，用于快速诊断；长待机验收仍必须使用更长窗口。此值不作为正式播放器定时规则。

## 实验规则

每轮只改一个变量。先做最小音频实验，后做全屏与完整播放器；不将多个权限、目标 SDK、播放框架和服务类型一起修改。

使用同一段已知可播放的合成音频。第一阶段使用手机扬声器，第二阶段再测蓝牙，避免把音频路由混入后台启动问题。记录并恢复测试调整过的音量、路由和权限，不播放其他个人文件。

每个关键条件至少重复 3 次，分别记录实际延迟与结果，不只填写“能响”。初步通过后再增加未充电、长时间锁屏和隔夜测试。

需要先明确手机操作：

| 场景 | 操作与检查点 |
| --- | --- |
| S0 前台未锁屏 | 保持应用页面可见，作为基本播放对照 |
| S1 返回桌面 | 按 Home，不划掉卡片；等至少 30 秒后触发 |
| S2 保留后台并锁屏 | 返回桌面后熄屏；到点前不点亮屏幕、不打开应用 |
| S3 划掉最近任务 | 只划掉目标应用；分别测亮屏和锁屏，并检查是否被系统置为 stopped |
| S4 一键清理 | 独立测试，不能用 S3 的结果代替 |
| S5 设置中强行停止 | 作为负向对照；不把强行停止后的自行恢复设为普通应用的保证 |

初始时间至少设在操作完成后的 2 分钟，保存后检查日期和下次触发时间，避免在编辑期间过点。建议记录触发后 60 秒、5 分钟两个时长上限；短文件应循环到上限，不能把播放完一遍当成测试通过。

## E0：固定源码、测试包和设备基线

状态：已完成新包构建、真机安装及通知/精确闹钟等核心基线；部分厂商设置仍未核对，见实际记录。

1. 核对当前 Git HEAD、工作区改动及文档入口。当前已回滚的业务代码不自动恢复。
2. 确定最小实验实现的代码来源与保存位置。若需独立实验包，先说明 applicationId、数据和授权与现有包的区别。
3. 记录 APK SHA-256、签名摘要、applicationId、版本、targetSdk、compileSdk、对应提交和未提交差异；旧 build 目录中的 APK 不直接视为当前源码产物。
4. 记录 vivo 型号、完整 OriginOS 构建号、Android 版本、安全补丁、时区、充电状态和输出路由。
5. 分别记录精确闹钟、通知、全屏通知、自启动、关联启动、后台高耗电、标准电池优化豁免、最近任务锁定的实际状态；缺少菜单记为“不提供/未找到”，不能记为已授权。
6. 核对手机残留测试任务，尤其是此前的重复闹钟。只清理确认属于实验的任务，不清除应用数据。

输出：一份可追溯基线。源码、APK 或权限状态对不上时，不进入对照实验。

## E1：目标 SDK 对照

状态：已完成首轮 37/34 对照，34 锁屏单次成功；待 A-B-A 回切及每条件 3 次重复。

在同一份最小实现上分别构建 targetSdk 34 和基线目标版本（此前实验包为 37），compileSdk、服务类型、音频和业务逻辑保持一致。记录安装前后权限/AppOps；降级安装被拒绝时，不卸载用户应用解决，改用事先约定的实验包与一致的授权步骤。

先跑 S0、S1、S2。每次同时记录：
- 系统是否投递闹钟；
- 服务是否真正处于 foreground、声明的类型及系统允许启动原因；
- 焦点返回值、使用中权限能力、AudioTrack 是否实际开始。

如果只有较低 targetSdk 成功，应进一步核对平台限制和补丁；不能直接宣布永久降低 targetSdk。若两者都失败，按失败阶段进入 E2 或 E4。

## E2：音频焦点 AppOps 对照

状态：待执行；仅在“已送达且服务已启动，但焦点失败”时执行。

读取并保存实验包的 TAKE_AUDIO_FOCUS 原始有效模式，区分包级与 UID 级覆盖。仅在允许对该实验包做临时权限实验的范围内，将这一项改为 allow，其他条件不变，复跑同一场景；完成后恢复原始模式并读回确认。不能用全局 reset 代替恢复。

不照搬其他系统的 CONTROL_AUDIO 等操作，不改无关应用，不将 ADB 或 Shizuku 授权伪装成普通应用自行获得的能力。

判读：
- 原模式失败、allow 成功：支持焦点访问控制假设，但仍需设计普通用户可用的方案。
- 焦点获准但无声：转查 AudioTrack 状态、音量、路由和应用暂停原因。
- 闹钟没有送达：本轮不能检验音频焦点问题。

## E3：前台服务启动时机对照

状态：已执行部分。预先启动前台服务仍挡不住 vivo 手动上划；App 主动移除自身任务已取得一次完整听感确认。任务栈、SDK 37 与长待机仍需验证。

对比：
- A：等待期间没有常驻服务，到点由 AlarmManager 启动服务。
- B：用户在页面可见时主动启用保障模式，启动可见前台服务，再返回桌面/锁屏；仍由 AlarmManager 负责到点触发。

核对服务类型是否符合用途。不得用无声音乐、虚假定位或持续忙循环伪装保活。前台服务不等于 CPU 永远运行，也不等于一定获得音频焦点。

先比较 S1、S2，再比较 S3。若 B 优于 A，记录改善的是进程存活、服务启动还是焦点获取；评估通知、耗电和长时间待机后再决定是否做成可选产品功能。

## E4：OriginOS 授权与关闭后台行为

状态：部分执行。后台高耗电、关联启动均已对照，仍观察到手动划卡后 stopped 与预约消失。实验包未出现在自启动列表，后台锁定尚待验证。

在固定 APK 上逐项核对自启动、关联启动（如有）、后台高耗电和最近任务锁定；每次只改变一项并记录前后差异。标准全屏权限、厂商后台弹出、锁屏显示和通知亮屏也分别记录。

观察 S1～S4 下进程是普通退出、被冻结还是进入 stopped 状态。不能因进程不存在就认定闹钟必然失效，也不能把“划掉卡片”与“强行停止”等同。

若出现“声音正常但没有页面”，单独排查全屏通知与窗口生命周期，不再改音频代码。未经新的明确范围，不禁用厂商系统组件，不修改整机省电策略。

## E5：隔离播放器与输出路由

状态：待执行；在系统触发、前台服务与焦点状态可记录后进行。

先用简单的原生 MediaPlayer 播放固定本地音频，再与 Media3 比较，保持调度和服务条件一致。这是对播放 API 的最小对照，**不是借鉴或移植 Fossify Clock**。

扬声器验证通过后再加入蓝牙，分别记录实际 AudioAttributes、输出设备、STREAM_ALARM/STREAM_MUSIC 音量、AVRCP 变化、焦点丢失与耳机断开事件。真正断开耳机与临时更换设备编号分开测试，避免自动切到扬声器造成意外外放。

状态：部分完成，见[全屏、手册与倒计时记录](2026-11-17-全屏手册与倒计时.md)。正式包在 vivo 开启“锁屏显示”后，18:26 全屏动画可见，用户确认并点击停止；此前页面被阻止时音频仍持续。收起继续播放、替换实例的设备验证及长期重复仍待执行。

- 在正常播放方案上加入全屏通知，记录通知发出、Activity 创建/恢复/结束、结束调用位置和播放状态。

## 阶段通过标准

初步实验目标：每个声明支持的场景连续 3 次触发成功；以计划时刻后 5 秒内开始播放作为初始观察阈值，记录实际值，不当成未经验证的产品保证。按约定时长停止，记录误差；页面收起不应导致声音停止。

短时测试通过后，至少再验证一次未充电的长时间锁屏和一次隔夜任务。只有完成这些结果及权限恢复，才能决定保留哪条实现路线。未覆盖的重启、进程回收和厂商系统版本明确列为未验证。
