# OriginOS 闹钟可靠性

目标是在 vivo 真机上找到可重复验证的定时播放方案：离开页面、锁屏或划掉最近任务后，到点能播放本地音频，并按设置的时长停止；全屏页面负责展示和控制，不应成为维持音频播放的必要条件。

更新日期：2026-11-17。状态：完成第一轮真机机制定位，见[基线](E0-2026-11-17/实验记录.md)与[真机记录](E1-2026-11-17/真机实验.md)。SDK 34 在允许后台高耗电后锁屏出声并按时停止；上划任务卡片仍导致 stopped 和预约消失。尚未通过重复与长待机验收。

## 源码与测试包不能混为一谈

2026-11-17 本轮文档整理时，Git 状态显示旧播放器、闹钟服务和多项测试处于删除状态；[项目说明](../项目说明.md)描述的是 Compose 模板。README、开发指南和部分历史记录仍保留此前完整播放器的介绍，存在阶段差异。

以下真机现象来自此前安装的实验 APK，不代表当前工作区还能编译出同一实现。下一轮必须先核对 APK、源码和签名，不能拿旧 APK 的结果证明当前源码，也不能自动恢复用户已撤回的改动。

此前本机调试签名与 GitHub Release 调试签名不同。用户曾自行卸载原包后安装实验版；后续不得再默认通过卸载解决签名冲突。

| 09:39 试听 | 播放器进入播放状态，30 秒后停止；当时闹钟音量为 0/150 | 不能用这次记录证明实际出声 |
| 09:45 返回桌面 | 系统有闹钟唤醒计数和前台服务启动豁免，应用没有接收触发记录 | 当时采用“智能控制后台耗电”；拦截位置未完全确认 |
| 10:00 锁屏 | 闹钟送达、前台服务启动，焦点申请连续返回 0，未开始播放 | 已改为“允许后台高耗电”；高耗电授权本身不足以解决 |
| 10:10、10:25 锁屏 | 先发全屏通知后，焦点从 0 变为 1；响铃页很快退出，准备阶段 15 秒超时 | 页面结束事件为 app-request；10:25 用户明确表示没有操作手机。具体 finish 调用原因尚未确认 |
| 蓝牙音量 | AudioTrack 为 USAGE_ALARM，同时系统记录了 STREAM_MUSIC 与 AVRCP 音量调整 | 输出为蓝牙 A2DP；不能承诺与媒体音量完全独立 |
| Fossify Clock | 用户测试：关闭后台，或保留后台但锁屏，均不能正常工作 | 用户反馈；版本、权限和完整日志尚未归档。不能据此证明所有 ROM 或所有版本都失败 |
| 模拟器 | 曾通过播放、冷启动、时长及全屏按钮测试 | 仅说明对应实验 APK 在模拟器通过，不代替 vivo 结果 |
| 真机 instrumentation | 一次在启动阶段卡住，被终止 | 没有有效通过结果；后续采用正常界面和日志验证 |

本轮新增决策：**不再以 Fossify Clock 为拟借鉴的实现，也不再将“换成 Fossify 的架构”列为修复路线。** 只保留其在同一设备上失败的对照信息。

用户最新复测为“保留后台或前台未锁屏可以触发，关闭后台或锁屏不行”。后续须拆分“返回桌面”“划掉最近任务”“一键清理”“设置中强行停止”，不能统称关闭后台。

## 待验证假设

- **Android 15 音频焦点限制或缺陷**：此前测试包目标 SDK 为 37，真机为 Android 15；系统曾同时显示允许启动前台服务与使用中权限能力被拒绝。与公开缺陷相似，但尚未证明该 ROM 缺少对应补丁。
- **OriginOS 启动或冻结策略**：自启动、关联启动、后台高耗电、标准电池优化豁免不是同一设置。此前只确认了部分授权。
- **应用自身生命周期问题**：响铃页自行请求结束是独立问题。焦点获准之后仍未进入播放状态，也不能继续归因于“闹钟没有送达”。
- **输出设备变化**：蓝牙路由切换、真正断连、静音和焦点丢失要分别记录；尚未证明蓝牙设备编号变化是本次故障根因。

## 研究依据与采用范围

- [Media3 #1815](https://github.com/androidx/media/issues/1815)：开发者报告 Android 15 后台焦点失败，维护者说明平台修复；用于确定对照实验，不等于本机根因已确认。
- [AOSP 移除音频焦点额外能力要求的修复](https://android.googlesource.com/platform/frameworks/base/+/5e40aee028ea)：证明平台曾存在超出文档预期的限制；本机是否包含修复待查。
- [目标 SDK 34 对照的开发者记录](https://stackoverflow.com/questions/79736477/no-audio-focus-in-foreground-service-in-android-15)：用于设计 E1，不作为长期降低目标 SDK 的决定。
- [Tasker 后台运行说明](https://tasker.joaoapps.com/userguide/en/faqs/faq-problem.html)：前台服务与可靠闹钟组合的产品实践；不保证绕过 OriginOS。
- [Alarmy vivo 指南](https://alarmy-android.zendesk.com/hc/en-us/articles/43868709190041)：核查厂商权限和锁屏展示条件，不直接照搬全部权限。
- [GrapheneOS 用户的音频 AppOps 排查](https://discuss.grapheneos.org/d/41661-vexing-issue-with-music-players-riplay-and-simpmusic)：仅作为 E2 线索，系统与设备不同。
- [vivo-guardian](https://github.com/Lokside/vivo-guardian)、[Service Keeper](https://github.com/sklndev/Service-Keeper)：仅列为外部守护候选；前者作者验证范围为 OriginOS 7 / Android 17，后者依赖 Shizuku，均不是本机已验证方案。

## 完成条件

需要有一组可复现的真机结果，说明所需授权、支持的后台状态、播放时长和已知限制，再决定产品实现。完成标准见实验计划；当前没有“锁屏和关闭后台已修复”的结论。

业务恢复与整合放在机制验证之后。后续仍以本地播放器为主，保留此前确认的播放列表、目录、睡眠定时、闹钟淡入和单次时长控制需求，不把它们误写成模板当前已具备的能力。
