# 开发指南

## 环境与构建

以下命令在项目根目录执行。SDK 路径由本机 `local.properties` 的 `sdk.dir` 指定，不应复制给其他开发者或提交个人路径。

使用项目自带 `./gradlew`，不安装全局 Gradle。版本依据在 [Wrapper 配置](../gradle/wrapper/gradle-wrapper.properties)、[Daemon JVM 配置](../gradle/gradle-daemon-jvm.properties)和[依赖目录](../gradle/libs.versions.toml)，修改时核对它们的兼容性。当前 Daemon JVM 要求 Java 25；Java 源码兼容级别不是 Gradle 运行时版本。

本机 Android Studio 位于 `/home/wushenhui/.local/opt/android-studio`，可这样执行构建：

```sh
JAVA_HOME=/home/wushenhui/.local/opt/android-studio/jbr ./gradlew :app:assembleDebug
```

成功条件为 `BUILD SUCCESSFUL`，且生成 `app/build/outputs/apk/debug/app-debug.apk`。首次构建需要下载 Gradle 和依赖；下载失败应先检查报错与网络，不直接更换依赖版本或关闭校验。

其他机器将 `JAVA_HOME` 换为匹配项目要求的 JDK；终端与 IDE 的 JDK 设置需核对一致。使用 IDE 时可直接选择设备后点击 Run。

## GitHub Actions 自动构建

[Android Release](../.github/workflows/android.yml) 仅在推送 tag 时运行；普通分支 push、PR 不构建，也没有手动触发入口。使用 Ubuntu 24.04、Temurin JDK 25、项目 Gradle Wrapper，安装 SDK 平台 `platforms;android-37.0` 和 Build Tools 37.0.0。

流程执行单元测试、Debug Lint 和 Debug APK 构建；全部成功后用 `gh release create --verify-tag` 发布对应 tag 的 GitHub Release，并附上 `app-debug.apk`。Release 说明明确标记为测试包。使用内置 GITHUB_TOKEN 和 contents: write 权限，不需要个人访问令牌。已发布 tag 不应移动；修改后发布新 tag。

APK 和测试报告同时上传到 Actions Artifacts，保留 14 天；失败时仍保存已生成的报告，不发布 Release。Release 附件不随 Artifacts 的 14 天保留期过期。

发布示例：提交并推送代码后，执行 `git tag -a v1.0.0 -m "ShiYin v1.0.0"` 和 `git push origin v1.0.0`。完成后在仓库 **Releases** 下载 APK，在 **Actions → Android Release** 查看测试报告。提交时包含 Gradle Wrapper 的 JAR 和 properties；不要提交本机 `local.properties` 或构建输出。

流程不需要配置 Secrets，生成的是临时调试签名 APK。不同运行之间以及与本机调试包之间的签名可能不同，不能保证覆盖安装；有保留数据、连续升级或正式发布需求时，需要单独配置固定签名密钥。不要通过卸载已有应用来绕过签名冲突，否则会丢失本地设置。

当前流程不运行模拟器或真机测试，也不生成正式签名包。CI 成功不能证明锁屏、后台闹钟和耳机播放可靠。

配置依据：[GitHub Ubuntu 24.04 环境](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md)、[setup-java](https://github.com/actions/setup-java)、[Gradle Actions](https://github.com/gradle/actions/tree/v5)、[产物上传](https://github.com/actions/upload-artifact)。本机已执行相同 Gradle 构建命令；GitHub 云端首次运行仍待推送后验证。

## 测试与设备运行

使用匹配的 JDK，在项目根目录按改动需要执行：

```sh
./gradlew :app:testDebugUnitTest
./gradlew :app:lintDebug
./gradlew :app:connectedDebugAndroidTest
```

最后一项需要已启动且授权的设备或模拟器。存在多台设备时，先确认测试对象；不要把 API 37 模拟器的结果记成 API 35 真机结果。

[PlaybackIntegrationTest](../app/src/androidTest/java/com/Huffer342/shiyin/PlaybackIntegrationTest.kt) 用静音 WAV 验证扫描、追加队列不中断、手动媒体模式、睡眠定时设置/取消/一分钟到期停止、5 秒淡入及 30 秒试听上限、Activity 停止后的真实闹钟触发和清理。运行约 3–4 分钟。测试需要 API 29 及以上，须先在系统设置授予时音“闹钟和提醒”。它会授予本应用音频/通知权限，并清理自己创建的歌曲和任务，建议使用专用模拟器。

保留应用安装状态的复跑方式：

```sh
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest
adb -s SERIAL install -r app/build/outputs/apk/debug/app-debug.apk
adb -s SERIAL install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb -s SERIAL shell am instrument -w -r com.Huffer342.shiyin.test/androidx.test.runner.AndroidJUnitRunner
```

成功条件为 `OK (N tests)` 且没有失败；当前全量设备测试为 10 项；本次导航与目录改动运行其中 8 项 UI 测试，未重复耗时的播放/闹钟集成测试。仅有 adb 退出码 0 不代表断言通过。新增的导航与编辑交互测试、测试音频导入方式见 [UI 设计与测试](UI设计与测试.md)。

[ScheduleTest](../app/src/test/java/com/Huffer342/shiyin/ScheduleTest.kt) 覆盖星期重复、过期单次任务、禁用任务、调休补班、跨年缺失日历、旧/重复/迟到触发、时区变化以及 JSON 往返与非法数据。模板加法和包名测试仍保留，不代表业务验证。构建与单元测试不能证明后台音频或耳机路由可靠。

手动安装和启动应用：

```sh
adb devices -l
# 将 SERIAL 替换为上一步选定设备的序列号。
adb -s SERIAL install -r app/build/outputs/apk/debug/app-debug.apk
adb -s SERIAL shell am start -n com.Huffer342.shiyin/.MainActivity
```

成功条件：安装返回 `Success`，应用打开并显示预期页面，无启动崩溃。记录实际设备和系统版本。安装前确认是自己的开发包；不要为解决签名或安装冲突直接卸载已有应用，以免丢失数据。

## 首版设备验收

使用自有测试音频，先确认音量，分别检查以下场景：

- 拒绝/允许本地音频权限、永久拒绝后进入设置、撤销权限后再次扫描或触发任务。
- 扫描、搜索、队列、进度拖动、循环/随机、通知栏与锁屏播放控制。
- 手动播放使用媒体音量；试听和定时使用闹钟音量。试听 30 秒结束，定时按设定分钟数停止。
- 有线、USB 和蓝牙耳机连接时实际输出；耳机断开是否暂停；来电或其他音频占用后的行为。
- 一次、星期重复、中国大陆工作日规则；补班周末、放假工作日、跨年缺数据与更新失败。
- 创建、编辑、禁用、删除多个任务；重启、改时区、撤销/重新授予精确闹钟权限后的恢复。
- 返回桌面、划掉最近任务、锁屏、Doze 和系统回收进程后是否按时播放。强行停止单独记录，不能算成普通进程回收。
- 文件被删除或解码失败时，应用内消息和获准后的异常通知是否可见。

模拟器用于快速检查，vivo Android 15 真机用于确认后台、电池限制和耳机输出。不得把 API 37 模拟器结果记成 API 35 真机结果。重启后首次解锁前的播放、关机播放及强行停止后的自动恢复不在当前支持范围。
