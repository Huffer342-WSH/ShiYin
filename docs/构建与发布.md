# 构建与发布

工作流：[Android CI](../.github/workflows/android.yml)。采用“同一次运行内构建一次、测试该 APK、发布该 APK”的流程，减少发布包与测试包不一致的风险。

## 触发规则

| 事件 | build | test | release |
| --- | --- | --- | --- |
| PR 指向 main | 是 | 是 | 否 |
| 合并 PR 或直接推送 main | 是 | 是 | 否 |
| 推送 v* tag | 是 | 是 | 两项成功后发布 |
| 手动运行 | 是 | 是 | 否 |

PR 检查用于合并前反馈，main 检查验证合并后的真实提交。建议在 GitHub 分支规则中将 build/test 设为必须通过；当前只配置工作流，没有擅自改仓库分支保护。版本 tag 不覆盖、不移动，失败后应修复并使用新 tag。

## 三个 job 与产物复用

1. **build**：JDK 25、SDK 37 / Build Tools 37.0.0，生成 Debug APK、AndroidTest APK，预编译单元测试。上传 android-apks 和 SHA256SUMS。
2. **test**：依赖 build，下载同次运行的 APK 并校验摘要；运行 JVM 单元测试及 Debug Lint，再在 Android 15/API 35 模拟器安装下载的两个 APK，执行 PlaybackVisualTest。显式检查 runner 的 OK 与失败标记，不能只看 adb 退出码。
3. **release**：只允许 push tag，且依赖 build/test 成功；下载并再次校验同一产物，发布 app-debug.apk 和 SHA256SUMS，不调用 Gradle、不重新签名。

Gradle setup-gradle 与 --build-cache 用于复用依赖和可缓存的任务输出；测试 job 在缓存未命中时可能重新编译 JVM/Lint 所需内容。Artifacts 用于可靠传递 APK，不能把缓存当作发布来源。没有跨 workflow 搜索“最近成功包”，避免误发不同提交的产物。

默认 token 只有 contents: read，只有 release job 获得 contents: write。PR 不接触签名或发布凭据。使用 pull_request 而非 pull_request_target 执行贡献者代码。

产物与报告保留 14 天；测试失败也上传已有报告。Release 附件长期保留。取消过时分支/PR运行，tag 发布不自动取消。

## 发布步骤

1. 修改 app/build.gradle.kts 的 versionName 和递增的 versionCode，添加 docs/releases/v版本.md。
2. 本地执行 assembleDebug、testDebugUnitTest、lintDebug、assembleDebugAndroidTest，检查必要的设备用例。
3. 提交并推送 main，确认 CI 通过。
4. 创建不可变版本 tag，例如 git tag -a v1.1.0 -m "ShiYin v1.1.0"，再 git push origin v1.1.0。
5. 等待三个 job 成功，核对 Release tag、APK 与 Actions 产物的 SHA-256。

tag 构建会检查 RELEASE_TAG 必须等于 v + versionName。手动运行即便选择 tag 也不发布，避免重复发布。

## 签名与验证边界

目前没有配置固定签名 Secrets，继续发布 **Debug 测试包**。GitHub runner 生成的调试签名可能随运行改变，与本机也可能不同；不能保证覆盖升级，不要通过卸载有数据的应用绕过冲突。正式连续升级应另行配置固定签名并保护密钥，本次没有生成或提交私钥。

CI 目前执行 JVM 单测、Lint、PlaybackVisualTest，未把全部历史设备测试纳入门禁。Android 15 模拟器不能替代 vivo 锁屏、厂商清理、隔夜和耳机真机验收。历史 v1.0.1 发布成功，不代表新流程已验证；本轮进展见工作记录。
