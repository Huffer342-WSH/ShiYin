# 开发、构建与发布

个人改动在 `dev` 开发。预发布可直接在已推送的 `dev` 提交上打 `pre-v*` 标签，发布任务会运行完整检查。正式发布从 `main` 打 `release-v*` 标签，推荐先等同一提交的 main CI 通过。

## 工作流

| 文件 | 触发 | 行为 |
| --- | --- | --- |
| [CI](../.github/workflows/android.yml) | PR → main、push main、手动 | 调用统一检查，不发布 |
| [Android Checks](../.github/workflows/checks.yml) | 仅被其他 workflow 调用 | 固定 GHCR 镜像内 Lint、JVM 单测、构建；宿主 KVM 模拟器回归 |
| [Release](../.github/workflows/release.yml) | push `pre-v*` 或 `release-v*` tag | 查找同提交 main CI，复用或重新检查，然后发布 |
| [Build Image](../.github/workflows/image.yml) | dev/main 上 Dockerfile、入口脚本或镜像 workflow 变化；手动 | 构建并推送 GHCR 工具链镜像 |

普通 `dev` 推送不会触发 App CI。外部贡献仍可通过 PR 触发检查。

## 同一 commit 的产物复用

Release 只选择本仓库 android.yml 中 push main 的运行，要求 head_sha 与 tag 解引用后的 commit 完全一致：

- CI 已成功、android-apks 未过期：跨 workflow 下载其原始产物，跳过构建测试。
- CI 正在运行：最多等待 15 分钟。
- 没有对应 CI、产物过期/缺失、等待超时：调用同一个 Android Checks，成功后才发布。
- 对应 main CI 已失败/取消：阻止发布，先处理 CI。
- PR 的虚拟合并提交、其他分支、其他 commit、其他仓库的运行都不能复用。

因此推荐先等 main CI 成功，再推同一 commit 的 tag。main 后又增加了提交，或修改版本号再打 tag，都属于新 commit，不能复用旧包。

CI 构建 Debug、测试和未签名 Release APK。发布时按提交选择 CI 运行，读取两份 APK 的包名与版本，确认 Release 关闭调试后签名。CI 的 APK 产物仅包含三个 APK。GitHub Release 只上传 `ShiYin-版本-debug.apk` 和 `ShiYin-版本-release.apk`。

| 推送的 tag | 构建版本 | GitHub 发布类型 |
| --- | --- | --- |
| `pre-v0.1.0`、`pre-v0.2.1` | 0.1.0、0.2.1 | Pre-release |
| `release-v1.0.0` | 1.0.0 | 正式版，标记为 Latest |

发布前更新 `app/build.gradle.kts` 中的 versionName、递增 versionCode，并整理[更新日志](../CHANGELOG.md)。tag 中的三段数字必须匹配 versionName。

GitHub Release 正文自动列出提交标题和短哈希。预发布从最近的预发布或正式版起算，正式版从最近的正式版起算。工作流沿当前提交的第一父链查找上一标签，从当前提交的父提交开始，因此同一提交上的预发布标签不会截断正式版说明。首次发布相应类型时，若没有符合条件的历史标签，则列出全部可达提交。

## 项目镜像

包名为 ghcr.io/huffer342-wsh/shiyin-build，OCI source 标签关联本仓库。镜像由 GitHub Actions 使用 GITHUB_TOKEN 发布，不在源码保存凭据；默认沿用仓库访问范围，不主动公开包。

[docker/android/image.txt](../docker/android/image.txt) 保存实际发布的不可变 digest。更新工具链时：先推 Dockerfile/入口改动至 dev，等待 Build Image 成功，下载 android-build-image artifact 中的新引用，再更新 image.txt 并推送 main 执行 CI。不要让 App CI 随 latest 漂移。

CI 的 Gradle 构建在该镜像里执行，无需重新安装 JDK/SDK；模拟器 job 仍直接使用宿主 KVM，并下载同次构建的 APK。只有镜像 job 具有 packages: write，发布 job 具有 contents: write；PR 仅有读取权限。

本地入口仍是 bash docker/android/run.sh，自行构建本地镜像，见[容器说明](../docker/android/README.md)。私有 GHCR 包的本地拉取需要个人 read:packages 授权；CI 使用仓库 GITHUB_TOKEN。

## 验证与产物

- JVM 业务单测运行 `:app:testDebugUnitTest :guard:testDebugUnitTest`，用例数见当次测试报告。
- Lint 运行 `:app:lintDebug :guard:lintDebug`。
- Android 15 / API 35 模拟器先安装用临时密钥签名的 Release 产物副本，检查首次启动能显示运行环境配置，关闭配置后能看到歌曲首页，并验证守护包同签名权限。随后安装 Debug 包运行 `PlaybackVisualTest`。发布任务使用原始未签名产物和发布密钥。
- 发布来源筛选另有 Node 内置测试，覆盖 commit/分支/事件/仓库、失败 CI、过期产物与复用路径。
- android-apks 保留 30 天，测试报告保留 14 天；Release 附件不随 Actions 产物过期。
- 模拟器运行前清理一次性 runner 中未使用的 .NET/NDK，检查至少 12 GiB 可用空间；不改开发者电脑。

Release 签名使用仓库 Secrets `SHIYIN_KEYSTORE_BASE64` 和 `SHIYIN_STORE_PASSWORD`，密钥库应只含一把发布私钥，密钥口令与库口令相同。升级 Release 需沿用同一密钥并提高 versionCode。Debug 使用构建环境的调试签名。两个包共用 applicationId，签名不匹配时无法覆盖安装。

Gradle 将同一构建类型的守护 APK 打入主包的 `assets/shiyin-guard.apk`。Debug 使用构建环境的调试证书。Release 构建先生成内含未签名守护 APK 的未签名主包；CI 启动检查与正式发布均调用[双包签名脚本](../.github/scripts/sign-release.sh)，先签守护 APK，替换主包内的文件，再对齐并签主包。脚本从最终 APK 提取守护包，校验两者签名。模拟器另检查实际安装后的同签名权限。下载入口仍只有主应用 Debug 和 Release 两个附件。

在本机签 Release 时，设置 `ANDROID_HOME` 和密钥库口令环境变量 `STORE_PASSWORD`，然后执行 `bash .github/scripts/sign-release.sh app/build/outputs/apk/release/app-release-unsigned.apk /path/to/keystore ShiYin-release.apk`。

参考：[跨运行下载产物](https://github.com/actions/download-artifact)、[GitHub Packages 发布](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images)。
