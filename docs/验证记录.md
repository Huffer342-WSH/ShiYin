## 0.2.0 Release 启动闪退与本地修复验证（2026-11-20）

vivo Android 15 的启动崩溃栈与 GitHub Release 的 R8 映射标识一致。原 APK 的 DEX 中，默认包里的 `ot` 继承了仅包内可见的 `kotlin.collections.i`；AndroidX Startup 初始化时抛出 `IllegalAccessError`。同次发布的 Debug APK 在该手机上可冷启动至权限弹窗。原 CI 只在 API 35 模拟器上运行了 Debug 的 6 项播放测试。

在同一台 API 37 模拟器上，原 GitHub Release 复现相同异常；改用全应用 R8 优化及 Android 默认优化规则后，使用临时证书签名并全新安装的 Release 可冷启动，界面检查读到「使用手册」，返回后读到「歌曲」。

同日 16:39，vivo V2463A（Android 15 / API 35）全新安装同一份临时签名 Release，手机 APK 的 SHA-256 与测试包一致（`c3cacada207d70299d659c858fe55fea8be38b4a592e046912dfa19fa0ba5ea5`）。首次冷启动 214 ms，返回关闭通知权限弹窗后显示使用手册，点击「知道了」进入歌曲首页。强停后再次冷启动 166 ms，新进程直接显示歌曲首页。两次启动期间的 crash 日志均未出现时音崩溃或 `IllegalAccessError`。

另用本地 amd64 Docker 镜像 `shiyin-build:jdk25-sdk37` 离线执行 GitHub CI 的 Lint、主应用单测、Debug、AndroidTest 与 Release APK 构建任务，全部通过。容器 Release 与前一轮宿主 Release 的两个 DEX 哈希均不同。容器产物经临时证书签名后全新安装到同一台 vivo，手机 APK 的 SHA-256 为 `07bbe2d4be0695684ba028c6f014b988bbeb1f19fe17163ff63162757f17f982`。首次冷启动 223 ms，显示使用手册并进入歌曲首页；强停后再次冷启动 155 ms，直接进入歌曲首页。本地镜像与 GitHub 固定镜像的配置摘要不同。本轮未执行远端构建。

## 可选守护包与最近任务划卡验证（2026-11-19）

在 vivo V2463A（OriginOS 5 / Android 15，`10AFA828MZ003A1`）上对可选守护包 `:guard`（`com.Huffer342.shiyin.guard`）完成实测，详细步骤见[2026-11-19 工作记录](工作记录/2026-11-19-最近任务划卡与MediaSession保活.md#方案-a可选同签名守护-apk设计与真机验证)：

- **桌面与最近任务无感化**：通过 `ShiYin` 内置 `assets/shiyin-guard.apk` 安装后无桌面图标，`GuardActivity` 点击「完成设置并隐藏卡片」后不留最近任务卡片。
- **反例（未开 vivo 后台权限）**：`:guard` 仅授予 `SCHEDULE_EXACT_ALARM` + `POST_NOTIFICATIONS`、保留默认「智能控制后台耗电」时，守护闹钟被系统延迟（+42s / +82s）或漏响（`1795081850`）。
- **正例（开启「自启动」「关联启动」和「允许后台高耗电」）**：
  - 最近任务**未加锁居中单卡上划移除**后，60 秒倒计时（`晨光 · AAC 示例`）于 `1795082259` 零秒延迟冷唤醒 `ShiYin`，`AlarmActivity` `+226ms` 展示并播放音频。
  - 最近任务**未加锁点击「清除全部 (×)」**清理主进程后，60 秒倒计时（`晨光 · AAC 示例`）于 `1795082476` 零秒延迟冷拉起 `ShiYin`（`pid=608`），`AlarmActivity` `+156ms` 展示并播放音频。
- **2026-11-20 焦点修复版**：有线真机四种组合均观察到冷启动、响铃页和未静音的闹钟音轨。锁屏清除全部轮，系统先后冷启动守护和主包，14:13:08 用户确认实际出声。前三轮的守护发送延迟为 12～149 ms，第四轮未取到精确预约值。[设备时间、进程与焦点证据](工作记录/2026-11-19-最近任务划卡与MediaSession保活.md#2026-11-20-焦点修复版真机复测)。
- **未验证边界**：拔线后的焦点拒绝与重试、设备重启恢复、长时间待机 / Doze、卸载通知点击和 Release 双包同签。

模拟器中的冷启动用例会关闭 Activity、释放所有客户端控制器、停止原有服务，再等待实际 AlarmManager 触发，并在重连控制器前确认 isPlaying=true 记录。它没有杀死 instrumentation 所在进程，不等于进程回收或国产 ROM 真机验证。
